# Phase 0 Research: Проекты из постоянного хранилища данных с изображениями

Часть Technical Context зафиксирована конституцией проекта без `NEEDS CLARIFICATION`. Ниже — обоснование
конкретных технических решений, специфичных для этой фичи (первая фича, добавляющая реальную доменную модель
в БД и реальный GraphQL query).

## 1. Слой доступа к Prisma в NestJS

- **Decision**: Завести `PrismaModule`/`PrismaService` (`apps/backend/src/prisma/`) — `PrismaService extends
PrismaClient implements OnModuleInit`, помечен `@Global()`, подключается один раз в `AppModule`.
- **Rationale**: Стандартный паттерн интеграции Prisma с NestJS DI; позволяет внедрять `PrismaService` в любой
  будущий `*.service.ts` без повторной инициализации клиента. До этой фичи в проекте не было ни одного
  реального потребителя Prisma Client — этот слой добавляется впервые.
- **Alternatives considered**: Импортировать `PrismaClient` напрямую в `ProjectsService` — отклонено: нарушает
  принцип V (сервис не должен управлять жизненным циклом внешнего клиента напрямую) и не переиспользуется
  будущими модулями.

## 2. Модель `Project` в Prisma-схеме

- **Decision**: Доменная модель с полями `id` (`String @id @default(cuid())`, но сид-скрипт передаёт
  осмысленные значения `"himnavigator"`/`"placeholder"` явно), `title`, `description`, `url` (nullable),
  `imageUrl` (nullable), `isPlaceholder` (`Boolean @default(false)`), `sortOrder` (`Int`), `createdAt`,
  `updatedAt`.
- **Rationale**: Поле называется `sortOrder`, а не `order`, чтобы избежать неоднозначности с SQL-ключевым
  словом `ORDER` и явно отражать назначение (FR-006 — управляемый данными порядок отображения). `url` и
  `imageUrl` — nullable, потому что карточка-заглушка не имеет ни ссылки, ни изображения (FR-003, FR-007).
- **Alternatives considered**: Автоинкрементный числовой `id` — отклонено, чтобы сид сохранял человекочитаемые
  идентификаторы существующих карточек и не создавал расхождений при повторных прогонах сида (upsert по
  стабильному `id`).

## 3. Название поля изображения

- **Decision**: Поле называется `imageUrl` (и в Prisma-модели, и в GraphQL-типе, и в frontend-типе), а не
  `image`, как было в первоначальной формулировке идеи.
- **Rationale**: В проекте уже есть точный прецедент именования — `ProfileInfo.photoUrl` (`entities/profile`)
  для точно такого же случая (ссылка на изображение). `imageUrl` явно указывает, что поле хранит URL, а не сам
  файл/бинарные данные, и сохраняет единообразие с существующим кодом.
- **Alternatives considered**: `image` — отклонено как менее точное (не ясно, ссылка это или файл) и
  расходящееся с уже принятым в кодовой базе именованием.

## 4. Frontend: клиент для GraphQL-запросов

- **Decision**: `graphql-request` (тонкий fetch-based клиент) в связке с уже установленным
  `@tanstack/react-query` — `useQuery(["projects"], () => graphqlClient.request(PROJECTS_QUERY))` в
  `entities/project/api/`.
- **Rationale**: Принцип VIII требует именно TanStack Query как единственный механизм кеширования/состояний
  загрузки на фронтенде. Apollo Client или urql принесли бы собственный кеш и стейт-менеджмент, дублирующий
  React Query, — избыточная инфраструктура (принцип X). `graphql-request` — это просто typed fetch-обёртка,
  не конкурирующая с React Query.
- **Alternatives considered**: `@apollo/client` — отклонено (двойной кеш, тяжелее, требует `ApolloProvider`
  поверх уже существующего `QueryClientProvider`); нативный `fetch` без вспомогательной библиотеки — отклонено
  как менее читаемо для GraphQL-запросов (ручная сборка `{query, variables}` и парсинг ошибок).

## 5. Хранилище изображений: S3-совместимый API, MinIO для разработки

- **Decision**: Backend не обращается к объектному хранилищу вообще — хранит и отдаёт через GraphQL только
  готовую ссылку (`imageUrl`) как обычную строку. Для локальной разработки в `docker-compose.yml` поднимается
  сервис `minio` (S3-совместимый API на порту `9000`, консоль на `9001`), с портами, проброшенными на хост —
  браузер посетителя обращается к MinIO напрямую по `http://localhost:9000/...`, минуя backend. Выбор
  провайдера для продакшен-среды (Yandex Object Storage, AWS S3 и т.п.) откладывается и не требует изменений
  кода — только смена значения ссылки в данных проекта.
- **Rationale**: Соответствует FR-009 (загрузка и администрирование файлов — вручную, вне объёма фичи) и
  принципу X (минимум инфраструктуры: ни AWS SDK, ни upload-эндпоинта, ни credentials в backend не требуется).
  MinIO — стандартный способ получить S3-совместимый API локально без внешнего облачного аккаунта, тем же
  паттерном, что Postgres в этом же `docker-compose.yml` (принцип IX).
- **Alternatives considered**: Подключить `@aws-sdk/client-s3` в backend для генерации presigned URL —
  отклонено: явно избыточно, раз загрузка ручная и файлы публично читаемы (presigned URL нужен для приватных
  бакетов/операций записи, которых на этом этапе нет). Реальный облачный бакет уже сейчас — отклонено, так как
  провайдер для продакшена ещё не выбран (Assumptions спецификации), а MinIO не блокирует последующую замену.

## 6. Публичный доступ к бакету и загрузка файла (ручной процесс)

- **Decision**: После `docker compose up` бакет (`project-images`) и публичная политика на чтение (anonymous
  `download`) настраиваются один раз вручную через консоль MinIO (`http://localhost:9001`) или CLI `mc`;
  файл `chmtch-screen.PNG` загружается туда же вручную тем же способом. Итоговый URL
  (`http://localhost:9000/project-images/chmtch-screen.png`) прописывается в сид-скрипте.
- **Rationale**: Прямое следствие FR-009 и Assumptions — встроенного интерфейса загрузки/управления файлами
  на этом этапе не существует осознанно; ровно один раз выполняемая ручная настройка дешевле, чем
  automation/init-контейнер ради одного файла.
- **Alternatives considered**: Automated bucket-init сервис в `docker-compose.yml` (контейнер с `mc` в
  `command`, создающий бакет и политику при каждом старте) — отклонено как избыточная инфраструктура для
  одноразовой операции (принцип X); при необходимости может быть добавлено позже отдельной задачей.

## 7. Frontend → backend: адрес GraphQL-эндпоинта

- **Decision**: Новая переменная окружения `VITE_API_URL` (пример: `http://localhost:3000` для локального
  `pnpm dev:backend`, `http://localhost:3001` при запуске через `docker compose up` — см. проброс портов
  backend в `docker-compose.yml`). GraphQL-клиент обращается к `${VITE_API_URL}/graphql`.
- **Rationale**: Сервис `frontend` в `docker-compose.yml` запускает `vite dev` (не production-сборку), поэтому
  Vite dev-сервер читает `import.meta.env.VITE_*` из переменных окружения процесса при каждом запуске —
  передать значение достаточно через `environment` в docker-compose, никакой build-time (`ARG`) инъекции не
  требуется (это стало бы отдельной темой только при появлении production-сборки фронтенда, что вне объёма).
- **Alternatives considered**: Хардкодить URL backend'а в коде — отклонено (ломается при любом изменении
  портов/окружения, не конфигурируемо, как и требуется по духу принципа X — простая, но явная конфигурация).

## 8. Общий тип `Project` между frontend и backend

- **Decision**: Добавить `Project`-DTO в `packages/shared-types` (`project.ts`), по образцу уже существующего
  `HealthCheckResponse` — простой `interface`, вручную синхронизируемый с GraphQL-типом и Prisma-моделью.
- **Rationale**: Пакет для этого уже существует и используется по этому назначению backend'ом; ручная
  синхронизация трёх мест (Prisma/GraphQL/shared-types) для одной небольшой сущности проще, чем внедрение
  GraphQL-codegen пайплайна (новый dev-инструмент, конфигурация, шаг сборки) — избыточно для одной сущности
  (принцип X).
- **Alternatives considered**: `graphql-codegen` для автогенерации TS-типов из схемы — отклонено на этом
  этапе как излишняя инфраструктура для одной сущности; может быть пересмотрено, если доменных сущностей
  станет больше одной-двух.

## 9. Инструмент запуска Prisma seed-скрипта

- **Decision**: `ts-node` как dev-зависимость backend, `"prisma": { "seed": "ts-node prisma/seed.ts" }` в
  `apps/backend/package.json` (документированный Prisma-стандарт для `prisma db seed`).
- **Rationale**: Официально поддерживаемый Prisma способ без дополнительной настройки транспиляции;
  `apps/backend/tsconfig.json` уже сконфигурирован для NestJS и подходит для `ts-node`.
- **Alternatives considered**: `tsx` — тоже рабочий вариант, но не даёт выигрыша здесь и добавляет ещё один
  инструмент вместо задокументированного Prisma-стандарта.

## 10. Тестирование

- **Decision**: Backend — Jest-юнит-тест `ProjectsService` (сортировка по `sortOrder`, маппинг nullable-полей)
  с замоканным `PrismaService`, без реальной БД. Frontend — Vitest + React Testing Library: юнит-тест
  `ProjectCard` (рендерит `CardMedia`, если `imageUrl` есть; не рендерит — если нет) и `ProjectsSection`
  (состояния загрузки/ошибки/пустого списка) с замоканным `entities/project/api`.
- **Rationale**: Продолжает выбор тестового стека из `001-personal-landing-page`; для нового резолвера
  достаточно unit-уровня (без поднятия реальной тестовой БД) — соответствует принципу X, интеграционные тесты
  против реальной БД не введены как отдельная инфраструктура на этом этапе.
- **Alternatives considered**: Интеграционный тест резолвера против тестового Postgres/testcontainers —
  отклонено как избыточная инфраструктура для одного query без мутаций на этом этапе.

**Output**: все технические решения зафиксированы, `NEEDS CLARIFICATION` в Technical Context отсутствуют.

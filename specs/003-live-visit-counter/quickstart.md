# Quickstart: Живой счётчик посещений

## Prerequisites

- Docker + Docker Compose установлены (сервисы `postgres`, `minio`, `backend`, `frontend`)
- Node.js LTS и pnpm — для запуска Prisma-миграции локально без Docker

## Запуск стека

```bash
docker compose up
```

Модель `VisitCounter` уже включена в `apps/backend/prisma/schema.prisma`; отдельного нового сервиса
docker-compose эта фича не добавляет (использует тот же `postgres`, что и `002-projects-db-images`).

## Применение миграции (если ещё не применена)

```bash
pnpm --filter backend exec prisma migrate deploy
```

или, при локальной разработке без docker:

```bash
pnpm --filter backend exec prisma migrate dev
```

**Ожидаемо**: в БД появляется таблица `VisitCounter` (миграция `20260826162113_add_visit_counter`); строка
с данными не создаётся заранее — появится автоматически при первом вызове мутации (FR-007).

## Валидация: мутация увеличивает значение (User Story 1)

```bash
curl -s http://localhost:3001/graphql \
  -H 'content-type: application/json' \
  -d '{"query":"mutation { incrementVisitCount { id count } }"}'
```

(порт `3001` — при запуске через `docker compose up`; при локальном `pnpm dev:backend` — `3000`)

**Ожидаемо**: первый вызов возвращает `{"data":{"incrementVisitCount":{"id":"main","count":1}}}`; каждый
следующий вызов увеличивает `count` на 1 (SC-001).

## Валидация: атомарность при параллельных вызовах (SC-002)

```bash
for i in 1 2 3 4 5; do
  curl -s http://localhost:3001/graphql \
    -H 'content-type: application/json' \
    -d '{"query":"mutation { incrementVisitCount { count } }"}' &
done
wait
```

**Ожидаемо**: после пяти параллельных вызовов финальное значение `count` увеличилось ровно на 5 относительно
значения до запуска — ни один инкремент не потерян.

## Валидация: блок на лендинге (User Story 1, сценарии 1–2)

1. Открыть `http://localhost:5173`, прокрутить до нижнего блока страницы.
2. **Ожидаемо**: под подписью "Посещений страницы" отображается число.
3. Обновить страницу ещё раз.
4. **Ожидаемо**: число увеличилось на 1 по сравнению с предыдущей загрузкой.

## Валидация: устойчивость к недоступности backend (сценарий 3, SC-003)

1. Остановить backend: `docker compose stop backend`.
2. Открыть/обновить `http://localhost:5173`.
3. **Ожидаемо**: блок счётчика показывает только подпись "Посещений страницы" без числа; ошибка не
   выводится на весь экран, остальные блоки лендинга (Hero, Навыки, Проекты — при недоступности backend
   Проекты также покажут своё собственное состояние ошибки/пустого списка) остаются работоспособны.
4. Запустить backend обратно (`docker compose start backend`) и обновить страницу — число снова
   отображается и продолжает увеличиваться.

## Валидация: сохранение значения между перезапусками (SC-004)

1. Запомнить текущее значение (например, через `curl`-запрос выше).
2. Перезапустить backend-контейнер: `docker compose restart backend`.
3. Выполнить мутацию ещё раз.
4. **Ожидаемо**: значение продолжается с того же числа (+1), не сбрасывается в `0`/`1` — подтверждает, что
   данные хранятся в PostgreSQL, а не в оперативной памяти backend-процесса.

# Phase 0 Research: Живой счётчик посещений

> Восстановлено задним числом по фактически принятым решениям в коммите `17dd6f0`.

## 1. Хранение значения: одна строка с фиксированным `id`, а не автоинкрементная таблица событий

- **Decision**: `VisitCounter` — одна-единственная строка (`id: "main"` по умолчанию), содержащая текущее
  агрегированное значение `count`. Не таблица логов посещений (по одной строке на визит).
- **Rationale**: требование — показать растущее число, а не анализировать историю визитов (нет отдельной
  User Story на аналитику/отчёты). Одна строка + атомарный `increment` — минимально достаточное решение
  (принцип X).
- **Alternatives considered**:
  - Таблица `VisitLog` (одна строка на посещение, `COUNT(*)` при чтении) — отклонено: избыточно для простого
    счётчика, требует агрегирующего запроса на каждое отображение вместо O(1) чтения/записи.
  - Redis-счётчик (`INCR`) — отклонено: вводит новую инфраструктурную зависимость только для одного числа,
    противоречит принципу X при уже имеющейся PostgreSQL.

## 2. Атомарность инкремента: `upsert` с `update.count.increment`, а не `read-modify-write`

- **Decision**: `prisma.visitCounter.upsert({ where: { id }, update: { count: { increment: 1 } }, create: { id, count: 1 } })`.
- **Rationale**: `increment` — атомарная SQL-операция уровня БД (`UPDATE ... SET count = count + 1`), не
  требует блокировок на уровне приложения и устойчива к параллельным запросам (FR-003/SC-002). `upsert`
  одновременно решает и создание записи при первом обращении (FR-007), без отдельной миграции-сида.
- **Alternatives considered**:
  - Прочитать текущее значение, увеличить в коде, записать обратно (`findUnique` → `+1` → `update`) —
    отклонено: классическая гонка чтения-записи при параллельных запросах, теряет инкременты.
  - Отдельный сид, создающий строку `main` заранее — отклонено: `upsert` покрывает этот случай без
    дополнительного шага разворачивания.

## 3. Значение по умолчанию для `id`: `@default("main")` в Prisma-схеме

- **Decision**: `id String @id @default("main")` — не UUID/cuid, а фиксированная строка-константа.
- **Rationale**: сущность в этой фиче принципиально единственная (один счётчик для всей страницы, не на
  посетителя/сессию) — предсказуемый фиксированный `id` проще для чтения кода и ручной проверки в БД, чем
  случайно сгенерированный идентификатор единственной строки таблицы.
- **Alternatives considered**: `cuid()`/`uuid()` как у `Project` — отклонено для этой модели: там
  множественность записей естественна, здесь — искусственно вносит вопрос "какой из ID использовать",
  когда правильный ответ всегда один.

## 4. Точка вызова: `useEffect` на mount фронтенда, а не мутация на backend при каждом HTTP-запросе страницы

- **Decision**: Увеличение инициируется явным GraphQL-мутационным вызовом с фронтенда при монтировании
  `VisitCounterSection` (guard через `useRef`, чтобы не сработать повторно при перерендерах).
- **Rationale**: сайт — SPA без сервер-side рендеринга и без отдельного backend-роута, отдающего HTML;
  единственная надёжная точка "страница открылась в браузере" — клиентский рендер компонента. Серверный
  подсчёт (например, инкремент при каждом `GET /` от Nginx/статик-хостинга) отсутствует как концепция в
  текущей архитектуре (Vite SPA, раздаётся статикой).
- **Alternatives considered**: инкремент на backend при каждом GraphQL-запросе `projects` (раз он и так
  выполняется при загрузке) — отклонено: неявная побочная логика в чужом резолвере, нарушает принцип V
  (единственная ответственность резолвера/сервиса) и делает счётчик посещений скрытой зависимостью от
  наличия блока проектов.

## 5. Обработка ошибки на фронтенде: скрыть число, не показывать ошибку

- **Decision**: `{data && !isError && <Typography>{data.count}</Typography>}` — при ошибке мутации просто не
  рендерится числовое значение; подпись (`label`) остаётся видимой всегда.
- **Rationale**: согласуется с Edge Case "недоступность источника данных" из `001-personal-landing-page` и
  `002-projects-db-images` — блок не должен ломать страницу или показывать техническую ошибку конечному
  пользователю; счётчик посещений — не критичная для основной цели лендинга (визитки) функциональность.
- **Alternatives considered**: показывать плейсхолдер/скелетон при ошибке — отклонено как избыточное для
  некритичного второстепенного блока; отсутствие числа при ошибке само по себе не ломает раскладку
  (подпись остаётся, `Stack` не создаёт пустых рамок).

## 6. GraphQL-операция: `Mutation`, а не `Query` с побочным эффектом

- **Decision**: `incrementVisitCount` объявлена как `@Mutation`, не `@Query`.
- **Rationale**: операция изменяет состояние сервера (увеличивает хранимое значение) — по семантике GraphQL
  и общепринятым конвенциям такие операции ДОЛЖНЫ быть мутациями, а не запросами, даже если также
  возвращают данные. Это первая мутация в схеме проекта (до этого — только `Query.ping`, `Query.projects`).
- **Alternatives considered**: `Query` с побочным эффектом (`query { incrementVisitCount { count } }`) —
  отклонено: нарушает базовую семантику GraphQL (query должен быть идемпотентным/безопасным для повторного
  выполнения, кэширования, предзагрузки), могло бы привести к неожиданным двойным инкрементам при
  автоматическом рефетче/предзагрузке query-клиентом.

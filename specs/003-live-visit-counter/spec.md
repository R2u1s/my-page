## User Scenarios & Testing _(mandatory)_

### User Story 1 - Посетитель видит растущий счётчик посещений (Priority: P1)

Посетитель, открывший лендинг, хочет видеть, сколько раз страницу уже посетили, — это создаёт ощущение
"живого" сайта, в отличие от статичной цифры-заглушки.

**Why this priority**: единственная пользовательская история фичи — замена заглушки на реальные данные;
весь объём фичи сосредоточен здесь.

**Independent Test**: открыть лендинг дважды подряд (например, обновить страницу) — отображаемое число
увеличивается на 1 при каждом открытии.

**Acceptance Scenarios**:

1. **Given** посетитель открывает лендинг, **When** страница полностью загрузилась, **Then** блок счётчика
   отправляет запрос на увеличение счётчика и отображает актуальное значение, пришедшее с backend.
2. **Given** посетитель обновляет страницу ещё раз, **When** блок счётчика снова успешно отработал, **Then**
   отображаемое значение больше на 1, чем при предыдущей загрузке.
3. **Given** backend временно недоступен или запрос завершился ошибкой, **When** блок счётчика пытается
   получить значение, **Then** страница не ломается — блок счётчика просто не показывает число (подпись
   остаётся видимой), остальной лендинг работает как обычно.

---

### Edge Cases

- Что происходит при повторном рендере/повторном монтировании компонента в рамках одной загрузки страницы
  (например, React StrictMode/HMR в разработке): счётчик не должен увеличиваться более одного раза за одно
  фактическое посещение — используется guard от повторного вызова в рамках жизни компонента.
- Что происходит, если мутация завершилась ошибкой (backend недоступен, БД недоступна): блок не показывает
  число, но не приводит к падению страницы (Edge Case унаследован от `001-personal-landing-page`,
  FR-010/Assumptions).
- Что происходит при одновременном открытии страницы несколькими посетителями: увеличение значения — это
  атомарная операция на уровне БД (upsert + increment), гонки записи не приводят к потере инкрементов.
- Первое посещение вообще (запись счётчика в БД ещё не существует): счётчик создаётся автоматически со
  значением `1`, а не требует отдельной ручной инициализации.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Система ДОЛЖНА хранить значение счётчика посещений в постоянном хранилище данных (не в
  оперативной памяти процесса, не в статичном конфиге фронтенда).
- **FR-002**: При каждой успешной загрузке лендинга система ДОЛЖНА увеличивать сохранённое значение счётчика
  ровно на 1 и возвращать обновлённое значение странице.
- **FR-003**: Увеличение значения ДОЛЖНО выполняться как атомарная операция хранилища данных, устойчивая к
  параллельным одновременным запросам (без потери инкрементов при гонке).
- **FR-004**: Блок счётчика на странице ДОЛЖЕН запрашивать увеличение значения не более одного раза за одно
  фактическое открытие/монтирование страницы в браузере посетителя.
- **FR-005**: Если запрос на увеличение счётчика завершился ошибкой (например, backend недоступен), блок
  счётчика ДОЛЖЕН отображаться без числового значения, но не ДОЛЖЕН вызывать ошибку рендера всей страницы —
  согласуется с общим Edge Case устойчивости к недоступности данных (см. `001-personal-landing-page`).
- **FR-006**: Подпись счётчика (текст рядом со значением, например, "Посещений страницы") ДОЛЖНА
  оставаться заданной в конфигурационном источнике данных (`entities/visit-counter`), не быть жёстко
  закодирована в компоненте отображения (согласуется с FR-011 фичи `001-personal-landing-page`).
- **FR-007**: При первом обращении к счётчику (запись в хранилище данных ещё не существует) система ДОЛЖНА
  автоматически создать запись с начальным значением, соответствующим первому посещению, без отдельной
  ручной инициализации администратором.
- **FR-008**: Программный интерфейс увеличения счётчика ДОЛЖЕН быть доступен исключительно через GraphQL
  (мутация), без отдельного REST-эндпоинта — согласуется с принципом VI конституции (GraphQL — единственный
  контракт, REST ограничен `GET /health`).

### Key Entities _(include if feature involves data)_

- **Счётчик посещений (VisitCounter)**: единственная запись с текущим числовым значением количества
  посещений страницы. Заменяет "заглушку" из `001-personal-landing-page` (FR-010) — та же концептуальная
  сущность, но теперь с реальным, хранимым и постоянно растущим значением вместо статичного числа.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Значение счётчика, отображаемое посетителю, увеличивается на 1 при каждой успешной загрузке
  страницы — проверяется последовательным обновлением страницы и сравнением отображаемых значений.
- **SC-002**: При одновременной загрузке страницы несколькими посетителями (или быстрых повторных
  обновлениях) итоговое значение счётчика соответствует фактическому количеству успешных запросов, без
  потерянных инкрементов.
- **SC-003**: При недоступности backend блок счётчика не приводит к видимой ошибке или сломанному макету —
  страница остаётся полностью работоспособной за пределами этого блока.
- **SC-004**: Значение счётчика сохраняется между перезапусками backend-процесса (данные не теряются при
  рестарте сервера, в отличие от гипотетического хранения "в памяти").

## Assumptions

- Единица подсчёта — каждая успешная загрузка/монтирование страницы в браузере, а не уникальный посетитель;
  дедупликация по IP/сессии/cookie не входит в объём этой фичи (нет требования различать повторные визиты
  одного и того же человека).
- Аутентификация и любая идентификация посетителя не требуются — счётчик полностью анонимен и публичен
  (согласуется с Assumptions `001-personal-landing-page` и `002-projects-db-images`).
- Хранилище данных — та же PostgreSQL-база, что и для сущности `Project` (`002-projects-db-images`); не
  вводится отдельная СУБД или кэш (например, Redis) для этой простой задачи (принцип X — минимум
  инфраструктуры).
- Эта фича полностью заменяет статичное поведение, описанное в FR-010 спецификации
  `001-personal-landing-page`; сам блок счётчика (расположение на странице, визуальное оформление, подпись)
  не изменяется — меняется только источник числового значения.
- Список проектов, профиль и остальные блоки лендинга, описанные в `001-personal-landing-page` и
  `002-projects-db-images`, этой фичей не затрагиваются.
